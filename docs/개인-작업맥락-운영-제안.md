## 3. 코팡에 적용할 최소 파일 구성

**아래는 최초 제안의 구성안이다.** 기본 4파일을 적용한 뒤 전체 보완 요청으로 WORK와 관련 정본/양식까지 추가했다. 실제 구성은 CURRENT·상태 README에서 확인한다. HANDOFF는 실제 인계가 처음 필요할 때 추가한다.

```text
kopang-refactored/
├── AGENTS.md                            # 채택한 읽기·갱신·범위 규칙
└── docs/
    ├── 개인-리팩터링-구조-계획.md       # 구조·이전 순서·검증 계획
    └── work-status/
        ├── CURRENT.md                   # 현재 작업·차단·다음 행동·근거 링크
        ├── DECISIONS.md                 # 합의한 결정·이유·적용 범위·대체 이력
        ├── OPEN-QUESTIONS.md            # 미결 사항·필요 근거·해결/철회 이력
        └── HANDOFF.md                   # 실제 중단·다른 세션 인계 때만 추가
```

| 파일 | 남길 최소 내용 | 중복하지 않을 내용 |
|---|---|---|

| `CURRENT.md` | 갱신일, 진행 작업 또는 진행 작업 없음, 연결된 계획/관련 결정·질문, 현재 차단, 다음 행동 하나, 검증 근거 | 전체 TODO·Task 상태·결정 전문·Git 상태의 실시간 복제 |
| `DECISIONS.md` | 날짜·주제, 확정한 내용, 이유·적용 범위, 합의 근거, 활성/대체됨 상태와 이전 결정 연결 | 질문·아이디어·assistant의 제안을 확정 결정으로 등록 |

결정·질문은 처음에는 단일 Markdown 파일 안의 날짜·주제 제목과 링크로 연결한다. 개별 Record 파일·ID 체계·Front Matter·WP/Stage 폴더는 실제 규모나 반복 문제가 생기기 전 도입하지 않는다. WORK는 전체 보완 요청에서 실제 계획으로 추가했다. 별도 TODO·roadmap·logs는 실제 필요 전 추가하지 않는다. 실행·검증 근거는 기존 계획·Git·필요한 결과 기록에 연결한다.

## 4. 작업 시작·중간·종료 규칙 제안

### 시작·재개

1. 채택된 `AGENTS.md`와 `CURRENT.md`를 읽는다. 진행 작업 없음도 명시적으로 확인한다.
2. Current가 연결한 계획의 해당 범위와 관련 Decision·Open Question만 읽는다. 실제 인계에서 재개한다면 HANDOFF도 확인한다. 연결 문서를 재귀적으로 전량 읽지 않는다.
3. 실제 작업 경로·branch·HEAD·dirty 파일을 확인한다. 과거 문서의 Git snapshot을 현재 상태로 사용하지 않는다.
4. 요청 범위·바로 할 일·차단을 짧게 브리핑한다. 문서와 실제 상태의 불일치는 먼저 알리고 사용자 작업을 임의로 복원·삭제하지 않는다.

### 작업 중

- 목표·차단·다음 행동이 실질적으로 바뀔 때 CURRENT를 갱신한다. 명령 하나마다 또는 메시지마다 상태 파일을 쓰지 않는다.
- 사용자와 합의한 결정만 DECISIONS에 기록한다. 현재 요청으로 이미 확인된 합의와 assistant 제안·가설·단순 진행 지시를 구분한다. 불확실한 내용은 결정으로 승격하지 않는다.
- 판단에 필요한 질문은 OPEN-QUESTIONS에 남기고, 실제로 작업을 막는 질문만 차단으로 표시한다. 해결·철회 때 이유와 관련 결정/근거를 남긴다.
- 기존 결정이 바뀌면 새 결정에서 대체 관계를 남기고 이전 내용을 삭제하지 않는다.
- 계획의 세부 작업 상태는 연결된 계획 한 곳에서 관리한다. CURRENT는 해당 범위와 다음 행동으로 안내한다.
- 상태 문서는 대표 작성자 한 명이 갱신한다. 다른 에이전트는 증거·제안을 반환하고 같은 파일을 동시에 수정하지 않는다.

### 종료·중단·인계

- 실제 결과·검증한 범위·미검증·차단·남은 일을 구분하고 CURRENT의 다음 행동과 맞춘다. 구현 완료·검증 완료·GitHub 반영을 같은 상태로 표시하지 않는다.
- 미결 질문의 상태를 맞추고, 확정된 결정만 기록한다. 과거 미해결을 해결된 것처럼 승격하지 않는다.
- 작업이 미완료이고 다른 세션/작성자가 복구 맥락 없이 재개하기 어려울 때만 HANDOFF를 작성한다. 재개 후에는 그 인계가 소비됐는지 표시하고 현재 진입점은 CURRENT로 유지한다.
- 미커밋 작업이 있다면 실제 dirty 상태와 보존 위치를 기록한다. WYBU의 clean-commit Checkpoint 제한을 그대로 적용해 인계 기록을 못 쓰거나 강제로 commit하지 않는다.
- 기록을 위해 자동 commit·push·merge하지 않는다. Git 작업은 그때의 사용자 요청 범위와 채택된 Git 규칙으로 판단한다.
- 기록에는 비민감 요약·필요한 파일/검증 링크만 남긴다. 비밀키·실제 환경값·개인정보·원문 대화·터미널 전체 출력을 복제하지 않는다.

## 6. 적용 범위와 남은 결정

- 가져올 것: Current 진입점, 관련 자료만 읽기, 결정과 질문 구분, 대체/해결 이력 보존, 필요한 인계, 실제 Git·검증 결과로 상태 판단, 대표 작성자 한 명.
- 가져오지 않을 것: WYBU Runtime·`capture_context`·candidate 승인 명령·UUID·WP/Stage ID·Hook·`.git/wybu` Store·Electron/Jev 규칙·주석 박스 강제·당시 작업공간 정리용 임시 사본.
- 해결한 결정: 최소 운영안 활성화와 파일 위치·이름은 0절과 DECISIONS에 기록했다. 남은 결정은 개인 학습 기록의 필요·위치, 인계 보존 기간과 실제 원격/CI 검증 환경이며 OPEN-QUESTIONS에서 관리한다. 개인 branch/worktree·PR 기본 절차는 이후 Git 규칙에 채택했다.
- 기본 AGENTS·Current·Decisions·Open Questions는 승인에 따라 적용했다. HANDOFF와 별도 기록 도구는 실제 필요가 생긴 뒤 추가한다. 앱 구조 변경과 Git 작업은 이번 적용 범위에 포함하지 않는다.

WYBU primary와 원본 코팡은 조사 대상으로만 읽었다. 다른 worktree의 dirty 작업을 수정·정리하거나 제품 Runtime을 실행하지 않았다.
