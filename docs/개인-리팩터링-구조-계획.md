## 1. 프로젝트 맥락과 문서 범위

이 저장소는 코팡 팀 프로젝트를 기반으로 한 개인 리팩터링·품질 개선 작업 공간이다. 원팀 커밋·기여자와 README의 팀 구성·담당 기록을 보존한다. 기존 팀 저장소를 변경하지 않고 개인 저장소에서 후속 개선을 진행한다. 기존 라이선스·출처가 있는 파일은 그대로 유지하며, 별도 라이선스 파일이 없다는 이유로 임의의 라이선스를 선언하지 않는다.

- 현재 실제 구조는 `frontend/`, `backend/`, `ml/`이다. 아래의 `apps/` 트리는 목표이며 아직 생성하지 않았다.
- [요구사항 정의서](./요구사항_정의서.xlsx), [API 명세서](./API_명세서.md), [DB 스키마](./DB_스키마.xlsx)는 기존 팀 기준 자료로 보존한다. 기능 계약·스키마 변경은 구조 이전과 별도 작업으로 다룬다.
- [기존 디자인 문서](../frontend/design/README.md)는 팀 프로젝트 당시 Web/Mobile 전체 분리 제안과 진행 기록이다. 개인 저장소의 후속 구조 방향은 이 문서에 기록한다.
- [DESIGN_SYSTEM.md](../frontend/DESIGN_SYSTEM.md)와 실제 `tokens.css`의 현재 값은 이전 중 기준으로 삼는다. 반응형 통합을 이유로 색·간격·브레이크포인트를 일괄 재설계하지 않는다.
- 기존 `frontend/TODO.md`·화면 구현 현황에는 과거 단계의 내용이 있다. 파일 이름이나 오래된 체크 상태만으로 기능 구현 여부를 판정하지 않고 실제 코드·라우팅·실행 결과로 확인한다.

현재 조회만으로 확인한 출발점이며 브라우저·build·DB 연동 회귀 검증은 아직 실행하지 않았다.

## 3. 합의한 목표 트리

아래는 책임 경계를 나타내는 목표다. 실제 파일을 옮기는 단계에서 필요한 폴더만 만들고, 예시 파일명·feature 목록은 해당 흐름을 검토한 뒤 확정한다.

```text
kopang-refactored/
├── apps/
│   ├── web/                              # 현재 frontend: React + TypeScript + Vite
│   │   ├── package.json, index.html, vite.config.ts
│   │   ├── public/                       # 정적 자산·MSW worker
│   │   └── src/
│   │       ├── main.tsx                  # React 실행·전역 스타일·개발 mock 시작
│   │       ├── app/                      # App·라우터·실제로 필요한 providers
│   │       │   ├── App.tsx
│   │       │   └── routes/               # 기존 URL과 페이지 연결
│   │       ├── layouts/                  # 사용자 shell·관리자 shell·계정 배치
│   │       ├── pages/                    # 주소별로 layout와 feature UI를 조립
│   │       ├── features/                 # 기능 UI·API·types·logic를 함께 배치
│   │       │   └── product/              # 예: 상품 조회 API·상태·상품 UI
│   │       ├── shared/
│   │       │   ├── ui/                   # Button·Input 등 업무와 무관한 UI
│   │       │   ├── api/                  # HTTP client·공통 응답/페이지 계약
│   │       │   ├── styles/               # 공통 token·기본 스타일
│   │       │   └── utils/                # 실제 여러 기능에서 쓰는 순수 함수
│   │       └── mocks/                    # 개발용 요청 handler·fixture
│   ├── backend/                          # 현재 backend: Spring Boot
│   │   ├── build.gradle, gradlew
│   │   └── src/main/
│   │       ├── java/com/kopang/app/
│   │       │   ├── BackendApplication.java
│   │       │   ├── domain/               # 업무별 Controller·Service·Mapper·DTO 유지
│   │       │   ├── config/               # 기존 설정 경계 유지
│   │       │   └── global/               # 공통 응답·예외·보안·S3 유지
│   │       └── resources/                # application 설정·MyBatis XML 유지
│   └── ml/                               # 현재 ml: 내부 폴더와 학습/예측 계약 유지
│       ├── model/train_churn.py, serve.py
│       ├── seed/, demo/
│       └── ddl.sql, requirements.txt
├── docs/                                 # 명세·개인 개선 계획·결정 근거
└── README.md                             # 소개·실행 경로·팀 기여·문서 진입점
```

- `apps/web` 안에 PC용 `web/`과 모바일용 `mobile/` 전체 트리를 다시 만들지 않는다.
- `app/providers`는 실제 전역 상태·소비자가 생길 때 해당 파일과 함께 추가한다. 폴더나 Provider 틀부터 만들지 않는다.
- `features/<기능>`마다 `api/`, `types/`, `logic/`, `components/` 하위 폴더를 강제하지 않는다. 파일 몇 개면 `api.ts`, `types.ts`, `useSomething.ts`, 컴포넌트를 함께 둔다.
- 업무 데이터가 있는 `ProductCard`는 product feature 후보다. 여러 화면에서 쓰인다는 이유만으로 모든 컴포넌트를 `shared/ui`로 보내지 않는다.
- `packages/`는 둘 이상의 앱에서 실제 소스 코드 공유가 필요해질 때 검토한다. 계약이 비슷하다는 이유만으로 TypeScript·Java·Python 공통 패키지나 별도 모노레포 도구를 만들지 않는다.
- 기존 이미지·디자인 문서·발표자료·테스트는 필요와 추적 상태를 확인해 보존한다. 간략 트리에 생략한 항목을 삭제하라는 뜻이 아니다.

## 4. 프론트 책임과 의존 방향

| 경계 | 맡는 일 | 분리할 일 |
|---|---|---|
| `main.tsx` | 실행 진입점, 전역 스타일, 개발 환경 mock 시작 | 주소별 화면·업무 상태 |
| `app` | App 조립, route·인증 경계 연결, 필요한 전역 provider | 기능별 API·거대 업무 컴포넌트 |
| `layouts` | header·footer·navigation·content 배치, 관리자 shell | 상품 조회·주문 취소 등 기능 처리 |
| `pages` | 특정 주소에 필요한 layout와 feature 조립, URL 파라미터 연결 | 같은 API 호출·검증·상태 처리의 복제 |
| `features` | 한 기능을 이해·검증할 UI·API·타입·상태·업무 규칙 | 다른 기능의 내부 구현을 직접 참조하는 연결 |
| `shared` | HTTP 기반 계약, 공통 스타일·기본 UI·실제 공통 순수 함수 | feature·page·route에 의존하는 코드 |
| `mocks` | 개발용 요청 응답과 재현 fixture | 운영 실행의 진짜 데이터·환경설정 |

기본 의존은 `main → app → pages/layouts → features → shared`다. Layout은 필요한 feature UI를 조립할 수 있다. 여러 기능을 연결하는 화면 흐름은 page에서 조립하며, 기능 간 내부 import나 `shared → features` 의존이 생기면 경계를 다시 확인한다. 폴더마다 `index.ts`를 만드는 방식이나 새 상태관리 라이브러리는 미리 도입하지 않는다.

기능 API는 `features/<기능>`에 두고 공통 Axios 인스턴스·응답 envelope·페이지 타입은 `shared/api`에 둔다. 현재 JWT 재발급 큐, session/local storage 선택, OAuth callback 복귀 경로는 이전 중 보존한다. HTTP client의 인증 결합을 어떻게 나눌지는 실제 호출자를 확인한 뒤 결정한다. 해결하지 않은 상태로 파일만 옮겨 의존 방향이 맞는 것처럼 표시하지 않는다.

## 5. 반응형 통합과 기존 URL 보존

1. 모바일·PC의 같은 기능에서 데이터 입력, API 호출, 상태, 사용자 행동, 성공·실패 결과를 비교한다.
2. 같다고 확인한 로직과 기능 UI부터 공유한다. 한 route page가 화면 폭에 따라 CSS grid/flex·media query로 배치를 바꾼다.
3. DOM·탐색·상호작용 차이가 큰 부분만 별도 컴포넌트로 둔다. 예를 들어 카테고리 sidebar와 작은 화면의 카테고리 선택 UI를 feature 내부에서 나눌 수 있다.
4. PC·mobile 조건문으로 페이지 전체를 다시 복제하거나 브라우저 기기 감지로 서로 다른 앱을 생성하지 않는다. 화면 폭이 바뀌어도 입력·조회·장바구니 상태가 보존되는지 확인한다.
5. 기존 `/products`와 `/web/products` 등을 공통 page로 연결할 수 있지만 URL 제거·redirect·쿼리 정규화는 별도 결정한다. 기존 링크와 deep link를 먼저 보존한다.

| 보존할 URL 예 | 확인할 계약 |
|---|---|
| `/`, `/mobile`, `/web` | 기존 홈 진입·보기 전환·새로고침 |
| `/products`, `/web/products` | `cat`·`sort`, 카테고리 선택, 무한 스크롤·추가 조회 |
| `/products/:id`, `/web/products/:id` | 같은 상품 ID, 리뷰·문의·찜·장바구니 동작 |
| `/login`, `/web/login`, OAuth callback 경로 | 로그인·토큰 재발급·기존 복귀 URL |
| `/checkout`, `/web/checkout`, 결제 결과·재개 경로 | 서버 검증·결제 승인·실패 복구·주문 ID |
| `/my/*`, `/web/my/*` | 실제 존재하는 경로와 Web 전용 경로 fallback |
| `/my/support*`, `/web/support*`, `/admin/*` | 고객센터 경로 예외·관리자 권한과 독립 navigation |

실행 착수 시 AppRouter의 전체 101개 Route를 기준 목록으로 고정하고, 위 대표 표에 없는 주소도 비교한다. 이는 당시 소스의 기준 개수이며 향후 기능 추가를 금지하는 숫자 제한이 아니다.

## 6. 단계별 이전 순서

한 단계에서도 앱·화면 흐름별 작은 변경으로 나눈다. 파일 이동과 기능·디자인 변경은 각각 검증 가능한 결과로 분리한다.

| 단계 | 범위와 산출물 | 다음 단계로 넘어갈 확인 |
|---|---|---|
| 0. 기준 확보 | 이 계획, 현재 Route·대표 화면·기능 차이·build/lint 결과 목록 | 현재 실패와 미검증 환경을 구분해 기록. 이번 문서 작업은 실행 검증을 수행하지 않음. |
| 1. CSS 사용 정리 | 기존 위치에서 미정의 토큰과 실제 중복 스타일을 좁게 정리 | 상품 카드·주문·계정 대표 화면의 색·굵기·상태를 양쪽 폭에서 비교. CSS 줄 수 감소를 완료 기준으로 쓰지 않음. |
| 2. 앱 경로 이전 | `frontend → apps/web`, `backend → apps/backend`, `ml → apps/ml`을 앱별로 이동 | import·실행 명령·정적 자산·설정/학습 입출력 경로만 필요한 만큼 조정. 앱별 실행·기존 URL/API/ML 계약 유지. |
| 3. 프론트 경계 정리 | App/routes, layout, 공통 HTTP/styles/ui와 실제 feature 소유 파일 분류 | 기존 동작·DOM을 우선 유지. 인증 client 결합을 확인하고 역방향 의존·순환 참조 방지. |
| 4. 계정 책임 추출 | WebAccountPages의 프로필·리뷰·주문 등 실제 책임을 한 묶음씩 feature에 배치 | 13개 기존 kind 연결과 해당 URL·상태·API·사용자 행동 비교. 화면 합치기 전에 책임 추출을 검증. |
| 5. 대표 반응형 통합 | 상품 목록을 첫 사례로 공통 데이터 로직·페이지·CSS 배치 검증 | 카테고리·sort·추가 조회·중복 제거·오류 계약을 결정한 범위만 통합. 기존 두 URL에서 검증. |
| 6. 흐름별 확대 | 상품 상세·장바구니·인증·주문/결제·계정·지원·관리자 중 검증 준비된 한 흐름씩 | 공통화가 가능한 부분만 통합. 결제·OAuth·권한 경계는 테스트 환경과 서버 결과 확인이 확보된 뒤 진행. |
| 7. 잔여 정리 | 실제 사용이 끝난 wrapper·옛 폴더·import·문서 경로 정리 | 모든 참조와 Route 비교 완료, 회귀 검증 결과 확인 후 삭제. `pages/`·`web/`를 초기에 일괄 삭제하지 않음. |

Backend의 `domain/config/global/resources`와 ML의 `model/seed/demo` 내부는 우선 유지한다. 앱 경로 이전에 필수인 경로 수정 외 API·DB 스키마·학습 계산·모델 계약 변경을 섞지 않는다. ML의 `ml/_` 등 README에 언급된 미존재 입력/아카이브가 필요한 단계라면 출처를 확인하기 전 생성기 실행을 진행하지 않는다.

## 7. 검증과 중단 조건

### 단계에 맞춘 검증

- 문서만 바뀐 단계: 링크·목표/현재 구분·합의 정합성·diff를 검사한다. build·앱 실행·DB 조작을 문서 작성의 통과 조건으로 붙이지 않는다.
- 프론트 변경: 현재 `frontend` 또는 이동 후 `apps/web`에서 기존 `npm run build`, `npm run lint`를 사용한다. 기존 실패를 먼저 기록하고 새 실패와 구분한다. 설치가 필요하면 실제 manifest·lockfile과 환경을 확인한다.
- 브라우저: 작은 화면 360/390px, 배치 전환 구간, 넓은 화면을 비교한다. 768/1280px는 검증 폭 후보이며 새 디자인 브레이크포인트 확정이 아니다. 기존 토큰·화면 기준을 확인해 최종 폭을 고정한다.
- 기능: 정상·loading·empty·error·재시도, 로그인/로그아웃·401 재발급, back/forward·deep link·쿼리, 폭 변경 중 상태, keyboard focus·가로 overflow를 확인한다.
- 구매·계정: 목록→상세→장바구니→테스트 결제→주문 결과, 프로필·찜·쿠폰·문의 등 바뀐 흐름의 API 결과와 중복 요청을 확인한다. 실제 결제나 운영 데이터 쓰기로 검증하지 않는다.
- Backend 경로 이전: 기존 Gradle build/test 및 필요한 API smoke를 환경에 맞춰 실행한다. 현재 `BackendApplicationTests`는 DB 조회와 출력/예외 catch 위주이므로 test 명령 성공만으로 DB 정합성·권한을 검증했다고 판단하지 않는다.
- ML 경로 이전: 합성 fixture로 학습 입력·모델 파일 경로·서빙 기동·`/health`·`/predict/churn` 입출력/피처 순서를 확인한다. 운영·원팀 공유 DB에 seed/demo를 실행하지 않는다.
- 끝에는 의도한 파일만 변경됐는지 확인하고 원팀 기여·라이선스·비밀정보 제외 상태를 유지한다. 새 자동 검증은 실제 반복되는 위험을 확인한 경우에만 추가한다.

### 해당 이전을 멈추고 재검토할 때

- 기준과 비교해 URL·쿼리·권한·토큰·결제·ML 계약이 달라지거나 정상 흐름에 회귀가 생김.
- 두 화면의 기능 차이·미구현 동작이 발견됐는데 통합 후 행동 기준이 결정되지 않음.
- 새 build/lint 실패·순환 의존·동일 업무 로직 복제가 생기거나 platform 조건이 페이지 전체로 번짐.
- 새 추상화·패키지·도구가 현재 실제 사용처 없이 필요하다고 주장됨.
- 관련 없는 dirty 파일과 겹치거나 출처가 불명확한 입력·실제 비밀정보·운영 데이터가 필요함. 값은 출력하지 않고 해당 범위와 재개 조건을 보고함.
- 필요한 브라우저·API·테스트 환경을 확보하지 못함. 미검증을 통과로 적지 않고 영향 범위와 다음 확인을 기록함.

문제가 난 변경 단위에서 복구·재검토하며, 사용자나 다른 작업의 기존 변경을 덮어쓰거나 공유 Git 이력을 재작성하지 않는다.

## 8. 개인 작업맥락 운영체계 적용

비교 대상은 Current·Decisions·Open Questions·Handoff와 AGENTS가 지정하는 읽기·갱신 운영체계다. 최소 파일·역할·시작/중간/종료 규칙과 원팀 지침 충돌 처리는 [개인 작업맥락 운영 제안과 적용 기록](./개인-작업맥락-운영-제안.md)에 남긴다. 초기 AGENTS와 CURRENT·DECISIONS·OPEN-QUESTIONS에 WORK·상태 운영 정본·Git 규칙·PR/Issue 양식을 보완했고 HANDOFF는 필요 시 추가한다. 원본 전체 대조와 적용성 판단은 [대조표](./WYBU-운영규칙-대조.md)에 남긴다. 실제 상태와 다음 행동은 CURRENT에서 관리하며 이 적용이 코드 변경 권한을 추가하지 않는다.

- 실제 WYBU는 `work-status/current.md → 연결된 WP plan.md → 필요한 decisions/open-questions/checkpoints` 순서이며 branch·commit·PR 상태는 Git/GitHub에서 확인한다.
- Current는 진입점, 결정은 합의·대체 이력, 질문은 미결·해결 이력, Handoff는 실제 미완료 인계만 맡는다. 코팡에는 이 역할을 단순 Markdown 파일로 적용했다.
- 과거 `work-status/questions`는 현재 `open-questions`로 옮겨졌다. 과거 재시작 제안의 snapshot·임시 검증 사본을 현재 상시 규칙으로 복사하지 않는다.
- 실제 파일과 함께 폴더 만들기, 기능 코드 함께 배치, 작은 검증 가능 결과, 필요에 따라 검증/절차 확장이라는 일반 원칙도 참고한다.
- WYBU Runtime·capture_context·candidate 승인 명령·WP/Stage/UUID·Hook·Electron/Jev·고정 worktree 경로·주석 박스 강제는 가져오지 않는다. 원팀 외부 worklog의 정본과 개인 리팩터링 상태를 분리한다.

WYBU 사례의 성과도 구분한다. 로컬 Git 확인 기준 PR #45는 Markdown 계획 문서 21개 변경이고, PR #46은 Renderer 컴포넌트 8개 추출과 UI 통합이다. #46의 `shell.css`는 64줄에서 1,426줄로 늘었으므로 CSS 감축 성과로 소개하지 않는다. 코팡도 문서 계획·책임 추출·반응형 통합·CSS 감소를 각각 실제 diff와 검증 결과로 평가한다.

## 9. 아직 미결정인 사항

- 반응형 통합 후 기본 URL과 `/web/*` 별칭을 장기적으로 유지할 방식, PC/모바일 보기 버튼과 저장값의 최종 동작. 초기 이전은 기존 URL을 보존한다.
- 상품 목록의 카테고리·sort URL 계약, 중복 제거·페이지 종료·필터 동작을 어떤 기준으로 통합할지. 현재 두 구현의 차이를 먼저 비교한다.
- `features` 이름과 세부 경계: product/category/search, account/auth/profile, orders/payment, admin/churn 등 실제 사용과 책임에 따라 정한다.
- 현재 HTTP client·logout·토큰 저장·화면 이동 결합을 나누는 최소 방식, 전역 Provider가 실제 필요한지.
- 공통 토큰의 누락 값과 반응형 배치 기준, 대표 화면·검증 폭·허용 시각 차이.
- Backend/ML 개인 검증 환경과 모델/fixture 준비, 과거 문서가 가리키는 누락 파일의 필요 여부와 출처.
- 개인 학습 기록의 실제 필요·위치와 인계 보존 기간. 최소 운영안의 활성화·파일 위치·대표 작성자 원칙은 해결했고 [열린 질문](./work-status/OPEN-QUESTIONS.md)에 이력을 남겼다. 원팀 외부 worklog와 정본을 분리한다.
- 개인 Git 기본 절차는 [Git 규칙](./git-workflow.md)에 채택했다. 실제 원격 보호/merge 설정·안정적인 CI와 테스트 범위는 미확인이다. 이번 문서화로 Git 설정을 바꾸지 않는다.

다음 작업은 앱 경로 이전의 대상·참조 경로·실행 명령·검증·복구 계획 작성이다. 이 계획의 CSS 정리는 구현 후보이며 이번 운영 적용으로 실행 순서나 코드 변경까지 승인된 것은 아니다. 실제 앱 이동·리팩터링은 구체적 범위와 검증 환경을 정리해 별도 사용자 승인을 확인한 뒤 시작한다.
